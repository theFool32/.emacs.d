
* Emacs Configuration

** Installation
*** Installing Emacs
Install =Emacs= with one of below ways:
**** emacs-plus
#+begin_src bash
brew install emacs-plus@31 --with-native-comp --with-modern-purple-flat-icon
#+end_src
**** jimeh/emacs-builds
#+begin_src bash
brew tap jimeh/emacs-builds
brew install --cask emacs-app-monthly
#+end_src

or
#+begin_src bash
cd .emacs.d
make install_emacs
#+end_src

**** Compile from the source code
Check for [[https://github.com/theFool32/build-emacs-macos][theFool32/build-emacs-macos]]

*** Installing this configuration
#+begin_src bash
git clone --depth 1 https://github.com/theFool32/.emacs.d.git .emacs.d
#+end_src

*** Prepare
#+begin_src bash
cd .emacs.d
make custom
#+end_src

When the environment variables changed, you should update them with
#+begin_src bash
cd .emacs.d
make env
#+end_src

Enjoy hacking!

** macOS Desktop Startup

After syncing this checkout to a Mac, install Emacs.app, Python 3,
CaskaydiaCove Nerd Font and Sarasa Term SC. Prepare the configuration as
described above, then preview the desktop setup:
#+begin_src sh
~/.emacs.d/bin/install-emacs-daemon --dry-run
#+end_src

Apply it yourself with:
#+begin_src sh
~/.emacs.d/bin/install-emacs-daemon
#+end_src

Use =--restart= to apply updated =init.el= to an existing daemon. The script
checks for modified user buffers, active terminal processes and Org clocks
before a graceful restart. If a normal GUI Emacs owns the default server,
save and quit it yourself first. Installation without =--restart= retains
an already managed daemon.

For a nonstandard app location, add =--emacs-app /path/to/Emacs.app=.
The installer derives paths from the current checkout, home directory and
Emacs.app; no username is hardcoded. It can be rerun after syncing updates.
Existing files are backed up under =var/desktop-backups/=; machine-specific
paths stay in ignored =var/emacs-desktop.json=. If =init-custom.el= has no
binding declaration, the installer adds =lexical-binding: nil=, preserving
its existing dynamic binding and settings. The example file includes it too.

The script installs:

- =~/Library/LaunchAgents/local.emacs.daemon.plist= from the shared template.
  It runs =--fg-daemon= at login, restarts after a crash, and logs to
  =~/Library/Logs/Emacs/daemon.log=. Standard =emacsclient -c= also works.
- =~/Applications/Emacs Client.app=, which Raycast can find as *Emacs Client*.
  Use that entry for client startup. The original Emacs.app remains available.
- A small include in =~/.hammerspoon/init.lua=, if Hammerspoon is installed.
  It loads =macos/hammerspoon-emacs.lua= for =Ctrl-Cmd-.=; other bindings stay
  intact. Choose *Reload Config* in Hammerspoon once after installation.

Both launchers call =bin/emacs-client= through the generated app entry
point. They focus an existing window without replacing its buffers, or
create a client frame when no graphical window remains. An empty new client
shows the displayed agenda buffer, with the home directory as its working
directory. Desktop launches start from home instead of Hammerspoon/Raycast's
directory; explicit file arguments retain the caller's directory and show
those files. After client initialization, Emacs uses the native macOS
activation function with ='activate=, then raises and focuses the target
frame. Avoid ='activate-front=: in Cocoa builds its implementation falls
through to hiding Emacs, despite the function's docstring.
=Cmd-Q= and =C-x C-c= close the client frame while the daemon keeps running.

Direct GUI startup and client frames use the same ef-owl theme, 14pt Latin
font and CJK font scaled by 1.1. Font setup runs after GUI frame parameters
are applied. Doom Modeline loads on the first graphical frame, after fonts
and the theme are ready, so its height uses GUI font metrics. Child frames
keep their own fonts.

When =+self/use-rime= is enabled, daemon startup preloads Rime and its native
engine after packages are ready, before accepting desktop launcher requests.
This moves initialization off the first input-method toggle without enabling
Chinese input in existing buffers. Direct GUI startup keeps lazy loading.
Preload failures are logged; a first-time deployment remains interactive.

** Org Plans
Capture tasks in =gtd.org=, select their periods, and update the original
task's state. The task pool shows only unfinished entries from =gtd.org=.
The regular agenda uses the original file list: =gtd.org=, =diary.org=, and
=routine.org=. Project files are not included.

Plan selection and the =pd/pw/pm= capture templates add the =plan= tag.
Use =M-x org-tags-view= and search for =plan= to find planned tasks.
The tag remains while any =FOCUS_*= or =PLAN_*= selection is recorded,
including past periods, and is removed when no selections remain. Dates and
day/week/month distinctions continue to use the properties.

Use =SPC ;= to open day, week, and month plans, in that order. Every row refers
to the original task. Changes made in the agenda update its state and refresh
progress counts.
Only =DONE= counts as completed; =UNDONE= and =CANCELED= are shown separately.
Current plans and their progress counts use the daily agenda files and their
archives. The legacy =done.org= file is read only when explicitly viewing a
historical plan, so opening the startup agenda does not scan old records.

In an Org task or agenda, use these local-leader shortcuts:

| Keys | Action                         |
|------+--------------------------------|
| , v d | Toggle today's plan           |
| , v w | Toggle this week's plan       |
| , v m | Toggle this month's plan      |
| , v h | Review this/last month and year |

In the agenda, mark several tasks with =m=, then apply a plan shortcut once.
A mixed selection is added to the plan; if all selected tasks are already in
the current plan, they are removed. Selection does not change scheduled or
deadline dates. Week identifiers follow ISO weeks, starting on Monday.

For a new task, use =SPC x= and select =p d=, =p w=, or =p m= to capture
directly into today's, this week's, or this month's plan. Dates are filled
automatically. Planning does not automatically select parent periods or carry
unfinished tasks into the next period; select them explicitly when reviewing.

Use =, v h= to open the review directly, with no period or date prompts.
The top compares this calendar month through today with the full previous
calendar month. Below it, a rolling year's monthly Goals totals appear newest
first, with task details collapsed by default. The first and last calendar
months in that yearly range can be partial.

Press =TAB= or =RET= on a month to see separate month/week/day Goals progress
and tasks grouped as pending, missed, completed, and canceled. Green, amber,
red, and gray distinguish the states; progress shows completed Goals divided
by all selected Goals, including pending, missed, and canceled Goals.
Groups sort by the latest selected plan date, newest first, then by title.
=TAB= also folds individual state groups; =RET= visits the original entry.
Each task is listed once per month, and
=r= refreshes the review. No additional package or saved report is needed.

Only Goals qualify: modern tasks with =FOCUS_DAY/WEEK/MONTH= or retained
=PLAN_DAYS/WEEKS/MONTHS= selections, and legacy goal items directly under
=Daily/Weekly/Monthly Goals= in dated trees. Legacy weekly spelling variants
and explicitly =ACT_*= tagged items with date-tree context are supported.
Ordinary archived tasks, inherited subtasks, and a lone =plan= tag do not
qualify. =CLOSED= is neither required nor used to choose a Goal's month.

Plans determine membership: daily dates, month identifiers, and week starts
(ISO Monday for modern plans, recorded start dates for legacy weeks).
A late completion remains in its planned month. Same-ID copies are merged,
and day/week/month selections count once in the combined monthly total;
their separate progress can overlap. The yearly total counts unique Goals,
so it need not equal the sum of monthly totals for multi-month Goals.

Reviewing reads archives and =done.org= on demand and does not modify source
files. Refreshing recalculates the ranges and Goal totals.
No separate review file is created.

To archive a closed task, open its original Org entry and press =, D=.
The entire subtree is moved into =diary.org= under the =CLOSED= date's
=Archived= heading, keeping IDs and plan properties. The source and diary
are saved. This explicit command is the only plan-related operation that
writes to the diary; no existing diary or done entries are migrated.

Replanning a task retains its previous selections in =PLAN_DAYS=,
=PLAN_WEEKS=, and =PLAN_MONTHS=. Removing a selection removes only the current
period. Dates overwritten before this support was added cannot be recovered.

The old diary-goal capture templates, ACT tag planning, and cross-entry state
copier have been retired. Existing =diary.org= and =done.org= content is
preserved; plan selection and historical queries do not modify these files.
No old records are migrated or rewritten. Plan selection changes only
=gtd.org=. Reviews read current or archived goal states; they do not reconstruct
the state as it was at a past period's deadline.
